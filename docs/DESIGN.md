# チリツモ — 実装の設計メモ（採用判断の記録）

基準：「個人資産管理アプリ_実装引き継ぎ仕様書 v1.0」（以下、仕様書）。
このメモには、仕様書の **推奨詳細設計** と **表現裁量** の部分について、実装で選んだ内容と理由を書く。
ここに書いた内容は実装側の判断で、ユーザーが一つずつ承認した仕様ではない。
確定要件（計算の意味・必須入力・無料運用・保存場所・バックアップ/復元）は変えていない。

## 1. 技術構成

| 項目 | 採用 | 理由 |
|---|---|---|
| 言語・フレームワーク | 素の JavaScript（ES Modules）。ビルドなし・実行時の外部依存なし | GitHub Pages に置くだけで動く。依存の更新切れや有料サービスに左右されない。Claude がいなくても読める・直せる量に抑える |
| 配信 | GitHub Pages（GitHub Actions で `app/` だけを公開） | テスト・資料を公開物から外せる。既定のブランチへ push するとテスト後に公開（ブランチ名に依存しない） |
| ルーティング | ハッシュ（`#/assets` など） | プロジェクト配下（`/money/`）・再読込・深いURLでも 404 にならない |
| 保存 | IndexedDB（トランザクション） | 仕様書 10.2 の第一候補。関連する変更を原子的に保存できる |
| PWA | manifest＋Service Worker（オフライン時だけキャッシュを使う） | ホーム画面に追加できる。インストールは必須にしない |
| テスト | `node --test`（計算・検証）＋ Playwright（ブラウザ操作・保存・復元） | 計算・欠測・重複防止・日付・復元の保護を自動で確かめる |

ファイル構成：

```
app/                 公開するもの（GitHub Pages）
  index.html, manifest.webmanifest, sw.js, css/, icons/
  js/core/           計算と検証（DOMに依存しない純粋関数。Node でもテストできる）
  js/data/store.js   IndexedDB への保存・読込・置換
  js/ui/             部品（シート・入力欄・グラフ・絵）
  js/views/          画面（ホーム・資産・記録・振り返り・サブスク荘・設定）
tests/unit/          計算・検証の単体テスト
tests/e2e/run.mjs    ブラウザでの受け入れ確認
docs/                このメモと検証結果
```

## 2. 金額・日付（仕様書 4章）

- 金額は円の整数。入力は全角数字・カンマ・「¥」「円」を補助として受け付け、小数・文字・NaN・Infinity・13桁以上を拒否（上限 999,999,999,999 円/件）。合計は安全な整数範囲を検査する。
- 0円は「確認した値」として保存できる。未入力（欠測）とは別。
- 残高はマイナスを銀行口座だけ許可（総合口座の貸越など、確認した事実を入力できるように）。投資・奨学金は0以上。
- 日付は `YYYY-MM-DD`、月は `YYYY-MM`、記録日時は `2026-10-08T21:05:00.000+09:00` のような時差付き文字列。
- 日本時間の今日は「UTC+9の固定オフセット」で計算（日本に夏時間はない）。UTC 文字列の切り出しはしない。
- 未来日の残高は「推計」としてだけ保存でき、実残高にはできない。

## 3. 口座と管理対象期間（仕様書 5.5「対象集合」）

口座ごとに次を持つ：

| 項目 | 意味 |
|---|---|
| `managedFrom` 管理開始日 | この日以降の月末で、この口座の実残高が必要になる |
| `startKind` | `existing`（以前から持っていた）／ `new`（この日に新しく開設＝それ以前は0円） |
| `managedUntil` 管理終了日 | この日に解約・完済・管理終了（この日以降の月末は対象外） |
| `endKind` | `zero`（解約・完済して0円になった）／ `untracked`（管理をやめた＝その後は不明） |

- 月 M の対象口座 = `managedFrom ≤ 月末 < managedUntil`。アーカイブは一覧の整理で、対象期間には影響しない。
- **比較の条件（追加の判断）**：2つの確定月の対象口座が同じなら比較できる。違う場合は次のときだけ比較し、理由を表示する。
  - 新しい月だけにある口座が `startKind = new`（開設前は0円と本人が登録している）
  - 古い月だけにある口座が `endKind = zero`（0円で終えたと本人が登録している）
  - それ以外（以前からある口座を途中から管理し始めた等）は前月比を保留し、「途中から管理を始めた口座がある」と表示（A09）。
  - 「開設前は0円」「0円で終えた」は、本人が明示的に選んだときだけ使う（無断補完ではない）。
- 管理開始日より前の残高を記録しようとしたら、確認のうえ管理開始日をその日に広げる。新規開設の口座では開設日より前の残高は記録できない。
- 残高の記録がある口座は種類（銀行/投資/奨学金）を変えられない（確定の合計の意味が変わるため）。記録のない口座だけ削除できる。

## 4. 残高履歴と訂正（仕様書 5.3）

- 残高記録：口座ID・金額・基準日・記録日時・実測/推計・月末終了時点の確認・訂正元（`revisionOf`）・取り消し日時・メモ。
- **記録は書き換えない**。訂正は新しい記録を作り、`revisionOf` で旧記録を指す。1件の記録を訂正できるのは1回だけ（系列は一本道）。取り消しは `invalidatedAt` を付けるだけで、物理削除はしない。
- 「有効な記録」= 取り消されておらず、まだ訂正されていない記録。
- 同じ口座・同じ基準日・同じ区分（実測/推計・月末確認の有無）の有効な記録があるときは、黙って追加しない。「訂正として保存しますか？」と確認する。無関係な同日記録を合算することはない。
- 推計は実測を上書きしない（区分が違うので別の記録。合計・月末確定には実測だけを使う）。
- 最新値：今日までの有効な実測のうち、基準日が最も新しいもの。同じ日では「月末終了時点」を優先。それでも複数あれば「同じ日に複数」と警告する（入力が新しいだけで基準日が古い記録を最新にしない）。

## 5. 月末確定（仕様書 5.4・5.5）

- 月末に採用できるのは、**基準日＝月末日・実測・「月末の終了時点として確認」付き・有効** な記録だけ。
  - 月末日に実測があっても終了時点か未確認なら「時点不明」と表示し、本人が確認すると（同額の訂正版として）採用できる。
  - 推計だけ・未登録・同日に複数は「不足」。今日の値・別日の値・前月の値・推計では補わない。
- 確定できる条件：月末日を迎えている／対象口座が1つ以上／すべての対象口座に採用記録がある。
- 確定は明示ボタン＋確認ダイアログ。確定レコードに「採用した記録ID・その金額・対象口座・合計・計算版・前の版」を固定して保存する。
- 状態は `未確定／確定／要再確認`。**要再確認は保存値ではなく毎回判定**（保存し忘れが起きない・復元後も同じ結果）：
  - 採用した記録が訂正・取り消しされた／対象口座が変わった／計算版（`CALC_VERSION`）が変わった → 要再確認。
  - 要再確認の月は比較やグラフに使わない（古い確定値を現在の実績として使わない）。
- 確定し直すと第2版…として追加され、前の版と理由をたどれる。「確定を取り消す」も版として残る。
- 前月比：対象月と直前月がともに有効に確定し、比較できるときだけ。直前月が未確定なら、それより前の直近の確定月から「8月末→10月末（2か月）」として表示し、「前月比」とは呼ばない。
- 月次グラフは確定月だけ。欠測は棒を描かず「未」と表示（0円・据え置き・補間にしない）。
- 確定や増減を「節約できた」「投資の利益」とは表示しない。

## 6. 支出・お金の動き（仕様書 6章）

- 種類：`expense`（支出）・`income`（入金）・`transfer`（振替/積立）・`repayment`（奨学金の元金返済）・`card_payment`（カードの引き落とし）。入力の主導線は支出。
- 支出の必須は金額とカテゴリーだけ。日付は日本時間の今日が初期値。メモ・支払方法・口座・ごほうびは任意。
- 振替は2つの別の口座（銀行/投資）が必須。返済は奨学金が必須、引き落とし口座は任意。
- 返済の利息が分かる場合は、利息だけを「その他」の支出として別の1件で記録する（元金とは分ける）。内訳不明なら「内訳不明」として返済額だけを記録し、勝手に分けない。
- どの記録も残高を自動では変えない。
- 編集してもIDは変えず、版（`revision`）を上げる。種類は変えられない。
- 削除は `deletedAt` を付ける論理削除（集計から外れる）。直後の「取り消す」で元に戻せる。サブスクの支払確認との結び付きは同じ変更で外す。
- 返金・立替・按分は未対応（未合意のため実装していない）。
- 贅沢マークの名前は **「ごほうび」**（★）。入力時・一覧からワンタップで付け外しでき、金額・集計には影響しない。
- 「大きな出費」は期間内の記録済み支出の金額順に自動で5件。
- 日付が分からない支払（月だけ）は `datePrecision = 'month'` で保存。月・年の合計には入れ、週の合計には配分せず「日付不明」として別に表示する。普通の支出入力でも「日付が分からない（月だけ）」を選べる。

## 7. サブスク荘（仕様書 8章）

- 契約（部屋）：名前・部屋番号・メモ・アーカイブ。部屋番号は 101〜104, 201〜… の空き番号。
- 契約条件は **適用日つきの履歴**（状態・料金・周期・支払日・無料期間の終了日・解約手続き日）。ある日の条件＝その日以前で最新の履歴。
  - 状態：内見（無料体験）・入居（有料）・退去（終了）。
  - 内見の料金欄は「内見後に予定される料金」（不明なら null）。内見中の現在の費用は0円、内見後の見込みは別に表示。終了日を過ぎても自動では有料にしない（「入居か退去を記録してください」と表示）。
  - 退去は「解約手続きの日」と「退去日（利用・課金が終わる日）」を分けて記録。退去日が未来なら「退去予定」。見込みの減少は「これからの見込み」と表示し、節約できた実績にはしない。
  - 料金不明（null）は0円と区別し、見込み合計に入れず件数で示す。
- 見込み：有料利用中の条件を年額（月払い×12、年払いそのまま）の整数で合計し、月額相当は最後に1回だけ丸める。
- 支払の確認単位（請求ID）＝ `契約ID|請求月`（例 `sub_…|2026-10`）。金額や日付を直しても変わらない。
  - 月払い：その月に有料利用中なら候補。支払日が分かれば、その日の条件の金額を候補にする。
  - 年払い：支払月が分かっていて、その月に有料利用中なら候補。
  - 候補は実績ではない。予定日を過ぎても「未確認」のまま。
  - 「支払った」→ カテゴリー「サブスク」の支出1件＋確認記録を **1トランザクション** で保存。確認記録は IndexedDB の `add`（同じIDがあると失敗）で、連打・再試行・別タブからの二重保存を防ぐ。保存中はボタンも無効。
  - 「なし」＝支払なし（支出は作らない）。取り消して未確認に戻せる。
  - 既に普通の支出として記録した支払は「記録済みの支出と結ぶ」で本人が選んで結び付ける（自動では結ばない。カテゴリーをサブスクに変えるかは選べる）。
  - 終了後の遅れた引き落とし等は「支払を追加」（`契約ID|請求月|x-…`）。
- 登録時の「いつから」の初期値は今月1日（以前から使っているサブスクでも、今月の支払候補が出るように）。

## 8. 端末内保存（仕様書 10.1・10.2）

- DB 名 `futokoro-machi`（デモは `futokoro-machi-demo`）。旧サブスク荘の `subseat:v1` には触れない。
- ストア：accounts / snapshots / events / contracts / contractTerms / paymentLinks / closes / meta（`state`＝リビジョン、`settings`、`device`＝最終書き出し日時など端末ごとの情報）。
- 保存は「変更の組み立て（純粋関数）→ 1トランザクションで保存（`durability: 'strict'`）→ 完了してから画面に反映・成功表示」。失敗したら画面の入力を残し、理由（容量不足など）を表示して再試行できる。
- **他タブ対策**：各書き込みで meta のリビジョンを確かめ、読み込んだ時点から変わっていれば保存せずに最新を読み直し、「もう一度保存してください」と伝える（入力は残る）。BroadcastChannel で他タブに通知し、画面に戻ったとき（visibilitychange）にも確認する。
- 起動時に全データを検証し、不整合があればエラー画面（自動の初期化・サンプル投入はしない）。エラー画面から「中身をそのまま書き出す（調査用）」と「バックアップから復元（検証済みのファイルで置換）」ができる。
- 起動時に `navigator.storage.persist()` を依頼し、設定画面に結果を表示。
- DB の構造の版を上げるときは `onupgradeneeded` の中で移行する（失敗すれば全体が中止され旧データが残る）。新しい版の DB を古いアプリで開いた場合は削除せずにエラーで止まる。

## 9. バックアップと復元（仕様書 10.3・10.4）

形式：

```json
{
  "appId": "futokoro-machi",
  "appVersion": "1.0.0",
  "schemaVersion": 1,
  "exportedAt": "2026-10-08T21:05:00.000+09:00",
  "note": "…",
  "data": { "accounts": [], "snapshots": [], "events": [], "contracts": [], "contractTerms": [],
            "paymentLinks": [], "closes": [], "settings": {}, "categories": [] },
  "summary": { "referenceDate": "2026-10-08", "counts": {}, "expenseTotal": 0, "latest": {}, "closes": {}, "subscriptions": {} }
}
```

- 書き出しは保存の順番待ちを終えてから、その一時点のデータで作る。ファイル名 `futokoro-machi-backup-YYYYMMDD-HHMM.json`。
- 「ダウンロード」と「共有（Android の共有シート → ドライブ等）」を用意。どちらも「書き出し（渡した）日時」として記録し、**ドライブへの保存完了とは表示しない**。最後の書き出しのあとに変更があれば知らせる。
- `summary` は書き出し時の集計（件数・最新の確認済み残高・月ごとの確定状態と純資産・記録済み支出・ごほうび・サブスク見込み）を、基準日を固定して計算したもの。
- 復元の手順：ファイルを選ぶ → 何も書き換えずに検証（アプリID・版・構造・金額・日付・ID一意性・関連付け・訂正系列・確定値の再計算・summary の一致）→ 件数の比較を表示 → 「今のデータを先に書き出す」→「置き換わることを理解しました」にチェック → 確認 → 全ストアを1トランザクションで置換 → 保存された内容を読み直して summary を再計算し、一致を表示。
- 新しすぎる版は拒否。古い版は `MIGRATIONS` の関数で順に移行してから検証する（現在は版1のみ）。
- 置換の途中で失敗したらトランザクションが中止され、既存データはそのまま。

## 10. Service Worker（仕様書 12.2）

- 担当は `sw.js` のあるディレクトリ（`/money/`）だけ。キャッシュ名は `futokoro-machi-shell-<版>` で、整理するのは自分の接頭辞のキャッシュだけ（同じドメインの `/subseat/` のキャッシュや localStorage には触れない）。1.1.0 まで使っていた書体のキャッシュ（`futokoro-machi-fonts-*`）も自分のものなので片付ける。
- 取得は「通信を優先、通信できない・5秒以上かかるときは保存した画面」。更新は push 後、次に開いたときに反映される。入力データは IndexedDB にあり、Service Worker の更新で消えない。
- 画面ファイルを増やしたら `sw.js` の `SHELL` に足す（単体テストで漏れを検出）。版を上げたら `VERSION` も上げる。

## 11. 名前・見た目（表現裁量）

1.2.0 で名前と見た目を作り直した（1.1.0 までの「ふところ町」の昭和レトロは、小道具や書体の飾りが多く、作り物っぽく見えるという声を受けて）。

- 名前：**チリツモ**（塵も積もれば山となる）。小さな記録と月末の確認が積み重なって山になる、という考え方。
  - 内部の識別子（端末内の保存場所 `futokoro-machi`、バックアップの `appId`、キャッシュ名）は互換のため最初の名前のまま。
    名前を変えても、すでに入力したデータやバックアップはそのまま使える。書き出すファイル名だけ `chiritsumo-backup-…json` に変えた。
- 方針：姉妹アプリ「サブスク荘」で好評だった作り方に合わせる。
  - **ロゴはドット絵**。文字（チリツモ）も1ドットずつ描き、昼は墨の文字に金の影、夜（ダーク）は金の文字がネオンのように光る。
    山のしるし＝上から塵（ドット）が降って、金色の山に積もる。アプリのアイコンは墨の地に金の山。
  - **画面の文字は端末の書体**（system-ui。Android では Noto Sans）を太め（800〜900）で使う。書体ファイルを同梱しない（1.1.0 の約7.7MBがなくなった）。
    日本語の字間を広げない。数字は等幅（tabular-nums）。
  - 色は **墨 `#19191c`・生成り `#f3f1eb`・黄色 `#ffc928`** が中心。押せるボタン（主な操作）は黄色で、下に硬い影（ドット文字の影と同じ考え方）。
    ダークは墨の地に同じ黄色。グラフの色は 1.1.0 と同じ（データ可視化の検証スクリプトで明暗とも確認済み：棒 `#2f5f9e`/`#5a8ad8`、ごほうび `#a8740c`/`#b8841a`）。
  - 紙の質感・二重枠・菱形の印・判子・消印・通帳・レシート・シール帳・レジの表示窓などの「小道具」はやめ、カードと一覧だけのすっきりした形にした。
- **チリツモ山**（ホーム）：月末を確定した月の数だけ地層が1段ずつ積もる（要再確認・未確定は数えない）。最新の月末が確定していると頂上に旗。
  純資産が減った月も、確定すれば1段（**金額の大小は表さない**。確かめた月の数）。空は日本時間の時刻で朝・昼・夕・夜に変わる。
  段の厚みは、月が少ないうちは厚く、増えると薄くして画面に収める。
- 月末の状態は **ブロック**（確定＝金色に✓、要再確認＝！、未確定＝点線の空き）。山の地層と同じ色。確定したときは金色のブロックが1つ降ってくる。
- 奨学金は **20マスのメーター**（当初の元金が分かるときだけ。分からなければ出さない）。
- カテゴリー・口座の種類・お金の動きの絵は **12×12 のドット絵**（おにぎり・容器・紙袋・ゲーム機・電車・飛行機・画面・箱／銀行・芽・角帽／硬貨・矢印・カード・星）。
  絵文字は使わない（端末で見た目が変わらない）。
- サブスク荘：姉妹アプリ「サブスク荘」と同じ建物（板張りの2階建て・外階段・自転車・ドット文字の看板）。窓のカーテンは部屋ごとに6色、夜は明かり。
  内見中は窓の角にリボン、退去予定は窓にテープ、空室はガラスだけ。窓を押すとその部屋へ（読み上げ・キーボードでは下の部屋の一覧を使う）。
- 減少や負の値は赤で責めない（符号で示す）。状態は色だけでなく文字・アイコンで示す。動きを減らす設定ではアニメーションしない。

## 12. 画面の大きさ（Galaxy Z Fold）

ユーザーの端末（Galaxy Z Fold 系）に合わせ、次の3つの形で使えるようにした。

| 形 | 幅の目安 | レイアウト |
|---|---|---|
| 閉じた画面（カバー） | 〜719px（例 412×915） | 上にロゴ、下に5つのメニュー、右下に「＋ 支出」。1段 |
| 開いた画面（内側） | 720px〜（例 760×860、横向き 860×760） | 左に縦のメニュー（アイコン・＋支出・5つのメニュー・設定）、内容は2段組み。入力は中央のダイアログ |
| 半分折る（フレックスモード） | Viewport Segments API | 横の折り目：入力シートを下半分に（上半分で内容を見ながら入力）。縦の折り目：右半分に |

- `manifest` の向きは `any`（開いた画面の横向きに対応）。`interactive-widget=resizes-content` で、キーボードが出ても入力欄が隠れにくい。
- 2段組みの中身は画面ごとに決めている（例：ホームは左＝チリツモ山と純資産・奨学金、右＝月末の確定・最近の動き。サブスク荘は上段の左に建物・右に部屋の一覧、その下を2段）。
- 320px（ポップアップ表示など）でも横にはみ出さないことを確認。

## 13. 口座の構成に合わせた機能（ユーザーから聞いた使い方より）

ユーザーの使い方（概要）：給与の口座（ふだん使い）と貯金の口座（奨学金の自動引き落とし・毎月の振替先）、NISA の積立、奨学金。

- **はじめの準備**：給与の口座・貯金の口座・NISA・奨学金をまとめて登録する（名前は一般的な呼び名で、変更できる。金融機関名・金額などの個人情報はアプリに埋め込まない）。
  「先月末から」を選ぶと管理開始日＝先月末日になり、続けて先月末のまとめ入力が開く。
- **月末のまとめ入力**：その月末に足りない口座の残高を1画面で入力し、1つの保存で記録（基準日＝月末・実残高・終了時点として確認）。
  「◯/◯ の終了時点の残高として記録」というボタンを押すことが、終了時点の値だと本人が確認する操作になる（自動で月末扱いにはしない）。
  「そのまま確定する」がオンで空欄がなければ、同じ保存で月末も確定する。1件でも失敗すれば何も保存しない。
- **いつもの動き**：毎月の振替（給与→貯金）・NISA の積立・奨学金の返済・給与などのひな形（名前・種類・口座・金額は任意）。
  `settings.quickMoves` に保存し、バックアップにも含める（参照する口座が存在しないものは復元で拒否、口座を削除したら参照を外す）。
  記録するときに呼び出して中身を確かめてから保存する（期日が来ても自動では記録しない）。記録自体は今までどおり任意。
- 給与の口座を本人が「自由に使えるお金」として使っていても、アプリの表示は仕様書の確定要件どおり「自由に使えるお金」とは呼ばない。

## 14. 将来へ回したもの・既知の制限

- 仕様書 3.2 の将来機能（自動連携・同期・クラウド認証・自動バックアップ・家族共有・現金/電子マネー・カード未払い・他の負債・予算・投資損益・高度な返済分析・通知）は未実装。
- 残高照合（予測残高・未照合差額）は未実装。振替・返済・カード精算の口座の記録は保存しており、将来の照合に使える。
- 返金・立替・按分は未対応。
- カテゴリーのカスタマイズ・合計月額だけのサブスク入力・旧サブスク荘からの移行は未実装（未合意・初期対象外）。
- 年払いの支払月が不明な契約は自動候補を出さない（「支払を追加」で記録できる）。
- サイト全体のアクセス制限はない（公開されるのは画面のプログラムだけで、入力データは端末の外に出ない）。
- 実機の Galaxy Z Fold・iOS/Safari では未検証（Chromium で画面サイズと折り目を再現して検証）。
